# TDD по задаче

Проверяй контракт поведения, не устройство реализации. Порядок и объём работы задаёт
[AGENTS.md](../../../AGENTS.md#проверки--только-необходимые); скилл не требует общего прогона.

## 1. До изменения: выбрать достаточные проверки

Кратко назови изменяемое поведение, реальный риск и подходящую проверку — в объявлении
работы, без отдельного большого плана тестирования.

- Найди существующее покрытие и вызывающий код. Используй или дополни подходящий сценарий,
  а не создавай параллельный набор. Новый helper сам по себе не требует отдельного теста.
- Для нового кейса ответь: какая конкретная поломка останется незамеченной без него
  и почему её не ловит существующая проверка? Количество кейсов определяется рисками,
  не квотой тестов, строк, процентов покрытия или сочетаний всех параметров.
- Выбери минимальный уровень, на котором ошибка действительно обнаруживается:
  чистое правило — домен/unit; HTTP-доступ, SQL и транзакция — соответствующая интеграция;
  взаимодействие компонентов — UI; критичная сквозная цепочка — браузер.
- Не повторяй все варианты одного правила на каждом уровне. Дополнительный уровень нужен,
  если защищает отдельную связь: например, правильный API не доказывает, что страница его вызывает.
- Изменение общего правила/DTO требует адресных проверок затронутых читателей и writers,
  не всех импортирующих его модулей. При миграции проверяй нужные ограничения,
  применение и сохранность данных на разрешённой копии, не рабочей базе.
- Права, деньги, остатки и атомарность не упрощай ради скорости: проверяй затронутые
  отказы, повтор, откат и конкуренцию там, где такая ошибка возможна.
  Mock репозитория не доказывает работу настоящего ограничения или транзакции БД.

## 2. Выполнить подходящий цикл

### Новое поведение или баг: Red → Green → Refactor

1. **RED.** До реализации добавь или уточни минимальный тест нужного поведения.
   Запусти его и увидь ожидаемое падение из-за отсутствующей логики/бага.
   Ошибка импорта, окружения или подготовки — не доказательство RED.
   Если тест сразу прошёл, проверь: поведение уже работает или кейс не воспроизводит проблему.
   Не ломай рабочий код ради искусственного красного результата.
2. **GREEN.** Реализуй согласованное поведение без дополнительных функций впрок.
   Повтори изменённую проверку; новое падение исправляй по причине, не ослаблением ожиданий.
3. **REFACTOR.** Упрости собственные изменения по главному правилу.
   После изменения исполняемого кода повтори только соответствующие проверки.
   Если код после GREEN не менялся, дополнительный повтор не нужен.

Цикл относится к поведению, не к каждому приватному методу или косметической правке.
Существующую реализацию и чужую незакоммиченную работу не удаляй ради соблюдения TDD.

### Рефакторинг без изменения поведения

- Сохрани существующие поведенческие проверки и их ожидания; подготовку можно адаптировать
  к новой структуре, не меняя обещанный результат.
- При недостаточном покрытии сначала зафиксируй важный текущий контракт адресным
  characterization-тестом. Он может сразу быть зелёным — новое поведение здесь не вводится.
- Если свежего результата нужных проверок нет, перед рискованной перестройкой проверь
  исходное поведение. После перестройки повтори затронутые проверки.
- Если меняется контракт, это уже не чистый рефакторинг: применяй RED для изменённого поведения.

### Тексты, оформление и документация

Тексты, отступы, документация и конфигурация без изменения поведения не требуют новых
поведенческих тестов: проверь изменённый артефакт или нужный вид адресно.
Если правка стилей/конфигурации меняет поведение, выбери проверку этого риска.

## 3. Запускать адресно

Указывай нужный файл и подходящий runner из README. Пример для начального состояния из корня проекта:

```bash
node --test tests/logic.test.mjs
```

Это пример команды, не обязательный набор для любой задачи.
Для крупного файла допустим фильтр названия, если он не исключает нужные соседние сценарии;
убедись, что нужные тесты действительно выполнились, а не получился пустой успешный запуск.

Не запускай автоматически корневые npm test / npm run test, test:db, общий lint или build.
Широкий локальный прогон нужен только по поручению или названному риску, который
адресный набор не покрывает; отсутствие CI само по себе не повод проверять весь проект.
Достаточные типы, линтер, сборка и браузер выбираются отдельно, не комплектом к каждому тесту.

### Если проверка упала

- Разбери вывод: дефект реализации, подготовки теста или среды. Исправляй причину,
  не подменяй недоступную проверку случайным более широким прогоном.
- После исправления повтори упавшие сценарии и проверки поведения, затронутого этим
  исправлением. Успешные независимые наборы повторять не нужно.
- Повтор упавшего запуска без изменений допустим для конкретной временной причины среды,
  не для перебора попыток до зелёного результата. Недоступную проверку явно укажи в отчёте.

## 4. Завершить проверку блока

На законченный блок один раз проверь реально затронутые связи. Если их уже подтвердил
выбранный набор на неизменённом коде, не запускай его снова ради итогового отчёта.
При дополнительном прогоне сначала назови причину расширения.

После БД-прогонов передай координатору оставленные тестовые ресурсы; завершение блока — по
[локальной гигиене AGENTS](../../../AGENTS.md#локальная-гигиена-ресурсов), не параллельно чужим тестам.

Работа проверена, когда выбранные сценарии выполнены, результаты понятны и конкретные
риски покрыты. В отчёте кратко назови выполненные проверки и непроверенное.
Прежние посторонние падения/предупреждения отделяй от новых; не чини их вне области задачи
и не объявляй весь проект зелёным по адресному запуску.

При написании/изменении тестов, mock или тестовых помощников прочитай
[антипаттерны](./testing-anti-patterns.md).

Принцип узких локальных проверок адаптирован из
[сетапа Peter Steinberger](https://github.com/steipete/agent-scripts/blob/1159adf26ad007df38b87debb107d3946008d38b/AGENTS.MD#L95);
его процедуры Git/CI и внешние стенды не переносятся.
