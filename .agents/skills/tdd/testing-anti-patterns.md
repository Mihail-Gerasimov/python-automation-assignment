# Тесты без лишних проверок

Справочник для написания тестов, mock и тестовых помощников.
Выбор набора и цикл разработки — в [TDD](./SKILL.md); здесь только ловушки.

## Что считать полезной проверкой

Тест защищает наблюдаемый контракт и ловит конкретную ошибку.
Для общего правила полезен unit-тест; дополнительный HTTP/БД/UI-тест защищает свою связь,
а не обязан повторять все комбинации нижнего уровня.

- **Тест на каждый helper.** Не нужен автоматически: внутренний метод может быть покрыт
  через публичный сценарий. Самостоятельное сложное правило проверяй отдельно, если это
  понятнее и надёжнее; не раскрывай приватный API только ради количества тестов.
- **Один assert — один тест.** Не требование. Статус, результат и отсутствие побочного эффекта
  могут подтверждать один исход. Разделяй независимые сценарии, не предложения со словом «и».
  Однородные границы удобно проверять таблицей без копирования подготовки.
- **Повтор одного сценария везде.** Не добавляй одинаковые варианты в домен, API, компонент
  и E2E без нового риска. Проверка SQL, прав или реального подключения страницы к API
  не является дублем проверки чистой функции.
- **Тест на внутреннее устройство.** Не привязывайся к именам приватных методов,
  порядку внутренних вызовов, количеству строк и произвольным классам/снимкам.
  Утверждение о тексте или стиле допустимо, если это действительно контракт задачи.
- **Все текстовые guards бесполезны.** Неверно: ограничения архитектуры, запрет утечек
  и границы импортов могут проверяться по исходникам. Убедись, что guard проверяет реальное
  правило, обходит нужные файлы и не зеленеет на пустом входе; он не заменяет runtime там,
  где ошибка зависит от исполнения.

## Mock: изоляция, не подмена проверяемой логики

- Не проверяй только существование mock или поведение, заданное самому mock.
  Не подменяй сервис, правило или запись, работу которых должен проверить сценарий.
- Вызов реального порта — допустимый наблюдаемый контракт: например, запрещённая покупка
  не вызывает списание; повтор не отправляет второе письмо; в gateway ушла правильная сумма.
  Сам по себе assert на вызов mock не делает тест плохим.
- Подменяй зависимость на осмысленной границе и понимай её побочные эффекты.
  Ограничение БД, rollback и конкурентное списание требуют настоящей интеграционной проверки.
- Фикстура должна соответствовать реальному типу/контракту и включать необходимые данные
  для проверяемой цепочки. Переиспользуй типизированные фабрики, не копируй огромный ответ
  с необязательными полями и не скрывай отсутствующие обязательные поля приведением типа.
- Если подготовка становится сложнее проверяемого поведения, пересмотри уровень теста,
  границу подмены и существующие помощники; не создавай новый тестовый фреймворк в задаче.

## Не получать ложную зелень

- Падение из-за импорта/окружения не доказывает воспроизведение бага.
  Пустой набор, пропуск теста и пойманная без проверки ошибка не доказывают исправление.
- Не ослабляй assert, не обновляй снимок и не меняй ожидания старого контракта только ради GREEN.
  Согласованное изменение контракта требует понятной причины обновления ожиданий.
- Временной и конкурентный кейс должен проверять конкретную границу/инвариант,
  а не полагаться на случайное ожидание или запускать все сочетания «на всякий случай».
- Используй штатную изоляцию и уборку данных, в том числе после падения.
  Тестовые удобства не должны добавлять фиктивные бизнес-методы в production-код.
- Удаление/объединение уже существующих тестов — отдельная проверка назначения и покрытия.
  Эта инструкция сама по себе не разрешает массовую чистку тестов.
