# Исполнение, профили и восстановление

Читай при делегации, работе с очередью или восстановлении, не для короткого ответа.
Это инструменты помощника, не часть решения тестового задания. Node 24; новый npm-пакет не нужен.

## Выбор и достаточность

Координатор читает код и задаёт `risks`: `permissions`, `money`, `migration`, `concurrency`,
`cross-module`, `architecture`, `uncertainty`. Отсутствие риска обосновывается сценарием.
Любой из этих рисков выбирает минимум `critical`; архитектура и неопределённость сами
по себе больше не включают Astra. Узкий read-only inspect без рисков — `scan`, остальные
задачи без рисков — `standard`. Имена моделей/effort — только в [config.json](../config.json).
Ручной `profile` требует `reason`; ниже минимума опуститься нельзя.

Дополнительные профили расширяют выбор, но не меняют автоматические минимумы:

| Профиль | Когда выбирать |
|---|---|
| `scan` | Узкий поиск, список файлов/полей/вызовов по понятным условиям |
| `scan-xhigh` | Сопоставить несколько связанных источников и восстановить карту вызовов без рискованного решения |
| `scan-max` | Глубокая ограниченная сверка по известным правилам с множеством зависимостей; результат только факты и ссылки |
| `standard` | Понятная реализация, локальный баг/рефакторинг, документация и обычные проверки без рисков |
| `critical` | Любой риск из списка выше; права/деньги/миграция не становятся задачей Luna при повышении effort |
| `advanced` | Много связанных состояний, условных ветвей и взаимодействий; нужно подробно проверить их согласованность |
| `intensive` | Нелинейный сбой, сложный порядок конкурентных операций, доказательство инварианта или противоречивые результаты нескольких источников |
| `parallel` | Ultra для основного координатора сложного блока с независимыми подзадачами; не профиль leaf-помощника |
| `architect` | Ограниченная консультация Astra по основаниям следующего раздела |

`reason` объясняет, какую дополнительную сложность должен разрешить выбранный effort,
а не повторяет «задача сложная». Результат предыдущего исследования прикладывай, если оно
уже было. Обязательной лестницы high → xhigh → max нет: заранее понятный сложный сценарий
можно сразу назначить достаточному профилю. Падение само по себе не повышает effort,
неизвестный исход изменяющей команды сначала расследуется. Rank — порог допуска по рискам,
а не обещание равной силы разных моделей или одинаковой стоимости effort.

Luna Ultra не поддерживается текущим каталогом. Sol Ultra использует делегирование,
а не просто увеличивает глубину одного исполнителя. Поэтому `parallel` зарезервирован
основному координатору: policy запрещает его выдачу в очередь leaf-помощников.
Это сохраняет запрет вложенного пула и общий предел до трёх необходимых помощников.
Модель/effort основной сессии выбирается пользователем в клиенте; конфиг её не переключает.
Доступность пары в каталоге не означает разрешение использовать её в любой роли.
Основание: [OpenAI Models](https://learn.chatgpt.com/docs/models) и
[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), сверено22.10.2026.

Профили управляют делегируемыми поручениями. Модель основной сессии этим файлом не переключается.
Неизвестный код сначала исследует достаточный обычный профиль. Число файлов, слово «сложно»,
дизайн/маркетинговый скилл, обязательность ревью и единичный упавший тест не основания для Astra.

## Когда подключать Astra

`architect` назначается явно с одним конкретным вопросом в `reason` и основанием `escalation`:

- `architecture-decision`: нужен выбор между минимум двумя разными решениями существующего
  контракта/схемы/границ модулей. В `options` перечисли варианты и существенные различия;
  риск `architecture` обязателен. Обычная реализация по уже принятому плану не подходит.
- `sol-blocked`: после адресной работы Sol осталась конкретная проблема. В `evidence`
  запиши, что Sol уже проверил, полученный результат и нерешённый вопрос; сошлись на факт
  текущего шага/попытки. Нельзя выдумывать предыдущую работу или повторять неизвестный исход.
- `user-request`: пользователь прямо выбрал модель/effort для этого поручения. В `instruction`
  приведи его указание. Общая просьба качественно/глубоко проверить не считается выбором Astra.

Без `user-request` Astra разрешена только для `read-only` inspect/plan/review. Выдавай ей
адресный выбор/диагноз/проверку спорного решения, затем возвращай реализацию и обычные проверки
Sol. Не отправляй каждой Astra весь план, историю и все файлы проекта; дай нужный контекст вопроса.
Основание и цитату оценивает координатор: проверка структуры не доказывает истинность текста.

Новые назначения Astra ограничены high. Профиль `deep` снят; Astra/max и Astra/ultra
отсутствуют в действующем словаре. Старое разрешение max не возобновляет его автоматически;
изменение этого потолка требует нового решения пользователя и обновления правил.
Прямое указание модели может разрешить иной режим, но не отменяет AGENTS и доступы проекта.

Предел одновременной работы Astra — `limits.maxConcurrentAstra` в config, сейчас одна:
учитываются все batch и прежний running deep из истории; штатные агенты и App Server используют ту же очередь.
Освободившиеся слоты можно занимать независимыми Sol/Luna, общий потолок AGENTS сохраняется.
Сбой, недоступность модели или отсутствие квоты не означают автоматический переход к Astra.

Примеры полей поверх обычного контракта:

```json
{
  "profile": "architect",
  "reason": "Выбрать хранение версий общей основы для двух действующих writers",
  "escalation": {
    "kind": "architecture-decision",
    "options": ["Неизменяемые версии с явной ссылкой", "Изменяемая запись с отдельной историей"]
  }
}
```

При `sol-blocked` вместо options — `evidence` с фактом работы Sol и оставшейся проблемой.
При user-request можно явно указать `requestedEffort`, он должен совпадать с текущим профилем.
Старая история, включая снятый deep, сохраняет фактическую модель/effort; pending со старым маршрутом не запускается.
Изменившийся контракт заводится новым поручением; допустимый retry проверяет актуальную политику.

## Контракт в очереди

Пример структуры (значения `files`/`checks` выбираются под реальную задачу):

```json
{
  "id": "menu-scrollbar",
  "batch": "example",
  "step": "X.1",
  "goal": "Скрыть только полосу прокрутки указанного меню",
  "mode": "implement",
  "change": "cosmetic",
  "signals": ["ui"],
  "risks": [],
  "files": ["dist/assets/styles.css"],
  "checks": ["Адресно проверить, что горизонтальная прокрутка сохранилась"],
  "dependsOn": [],
  "access": "workspace-write",
  "maxAttempts": 2
}
```

- `mode`: inspect / plan / implement / review / verify. Последние два и inspect — read-only.
- `profile`/`reason`: необязательный явный профиль и его конкретная причина; без них работают
  автоматические минимумы. Дополнительные effort не выбираются по ключевому слову в goal.
- `escalation`: основание явного architect по правилам выше; сохраняется в очереди
  и передаётся исполнителю вместе с `reason`, а не теряется при запуске.
- `change`: none / text / cosmetic / behavior / refactor.
- `signals`: product / conversion / ui / behavior / code. Это область, не разрешение
  на новую работу. При plan поведенческие проверки только проектируются.
- `files`: точные относительные файлы, включая важные входы проверки; без каталогов и glob.
  Это контракт и защита от конфликтов, не файловая ACL. В App Server `access` задаёт sandbox.
  Штатный агент наследует права родителя: текущий spawn не умеет сужать их отдельно.
  Инструкция read-only сама по себе не является технической изоляцией. Изменение объявленных
  файлов блокирует приёмку; выход за их пределы дополнительно проверяет координатор.
- `dependsOn`: уже заведённые поручения этого пакета, их результат должен быть принят и актуален.
- `reviews`: ID writer того же шага; независимый reviewer читает его результат awaiting_review.
  Это не разрешение начать следующий шаг до приёмки текущего.
- `reuseFrom`: необязательный ID принятого поручения того же пакета, режима, доступа,
  файлов и инструкций. Только для действительно совместимого продолжения; review всегда чистый.

Очередь `.codex/orchestration/queue.json` содержит попытки, thread/turn либо native agent ID,
отпечатки файлов/инструкций и результаты. Она локальная, не коммитится и не заменяет фазу.
У неё один lock-владелец; до 128 поручений. Архивирование завершённых пакетов — отдельная
операция после сверки зависимостей, автоматического удаления/обнуления нет.

## Команды координатора

Все команды из корня текущего проекта. JSON передаётся аргументом, не создавай копию ТЗ.

```bash
npm run orchestration -- route --json '<контракт JSON>'
npm run orchestration -- status
npm run orchestration -- enqueue --json '<контракт JSON>'
```

### Штатные агенты — основной путь

1. `claim --batch <пакет> --capacity <фактически свободные слоты>` сохраняет попытки ДО spawn.
2. В штатный spawn передай короткий контракт, назначенные скиллы, **model и reasoning_effort**
   из route; для явной модели текущий инструмент требует `fork_turns: none`.
   Маркер `ORCHESTRATION_WORKER` запрещает рекурсивную делегацию.
3. `bind <id> --json '{"attemptId":"…","agentName":"…","model":"…","effort":"…"}'`.
   Записывай реальные параметры вызова, не подменяй отсутствие контроля моделью из таблицы.
   Повтор той же привязки допустим; другого исполнителя в ту же попытку записать нельзя.
   При достоверном отказе spawn ДО создания агента: `abort-claim <id> --json
'{"attemptId":"…","notStarted":true,"reason":"подтверждённый исход отказа"}'`.
   Это закрывает только свою попытку в needs_review; неизвестный исход так не помечай.
4. После результата и сверки текущего агента: `finish <id> --json
'{"attemptId":"…","status":"completed","summary":"проверки и ограничения"}'`.
5. Координатор проверяет изменения и необходимые доказательства, затем `accept <id>
--evidence '<что фактически проверено на итоговом коде>'`. Фазу отмечает отдельно по AGENTS.

Переиспользование штатного агента допустимо при совместимых инструкциях и неизменном
профиле. Если follow-up инструмент не меняет модель/effort, новый профиль требует нового
исполнителя или поддерживаемого App Server, а не фразы «переключись на другую модель».

### App Server — альтернативный путь

`doctor` делает только initialize, model/list и skills/list; **turn/start не отправляет**.
Проверка каталога не доказывает остаток квоты/entitlement на каждый реальный запрос.

`run --batch <пакет> --capacity <подтверждённые свободные слоты>` исполняет готовые поручения
через `codex app-server` по stdio. Не запускай его дополнительно к нативному пулу в обход лимита.
Настройка максимума 6 применяется при следующем запуске клиента; доступный лимит может быть ниже.
Явные model/effort/skill передаются на каждый turn; несовместимые/отсутствующие — отказ без
тихой замены. Для совместимого `reuseFrom` используется thread/resume, иначе чистый thread.
Вложенные агенты выключены. Запросы новых доступов/подтверждений отклоняются.
Workers не запускают операции с рабочими БД, Docker/стендом, production и Git; их ведёт
координатор в отдельно разрешённом процессе. Sandbox не поднимается до full-access.
Ограниченные сети/инструменты могут сделать нужную проверку недоступной — это ограничение,
не основание выдать непроверенное за успех или автоматически расширить полномочия.

RPC сверен с установленным Codex CLI 0.166.0: skills/list использует cwds/forceReload;
контроль собственных фоновых терминалов — experimental API. При обновлении клиента проверяй
совместимость, не копируй новые поля документации без проверки локальной схемы.
Источники: [App Server](https://learn.chatgpt.com/docs/app-server),
[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Стоп и восстановление

### Завершение помощников

После приёмки связанного блока координатор закрывает ненужных помощников. Когда согласованная
задача закончена целиком — итоговые проверки пройдены, результаты и ограничения сохранены
в поручениях/проектных документах, конкретных доработок и запланированного продолжения
в этих потоках нет — удаляет её дочерние сессии вместе с журналами. Это постоянное поручение
заказчика; повторное согласование для таких сессий не требуется. Завершения всей фазы или
других независимых задач ждать не нужно.

`turn/completed` сам по себе не запускает удаление. При незавершённой приёмке, нужном
follow-up/`reuseFrom`, паузе, стопе или неизвестном исходе команды сохраняй сессию и контекст
восстановления; ненужную активную работу останови по правилам ниже. Закрытый поток не возобновляй
ради нового поручения после завершения задачи: передай сохранённые факты новому исполнителю.

Порядок координатора:

1. Сохраняет результат, проверки и фактические модель/effort в поручении. До приёмки не
   закрывает помощника, если ему ещё нужно конкретное исправление или пояснение.
2. Определяет точные UUID своих дочерних сессий по parent/ancestor ID. Краткий список агентов
   может не показывать уже выгруженных детей; для удаления журналов сверь также список потоков.
   Для отдельного App Server runner принадлежность подтверждают запись собственного
   `thread/start` в попытке текущего пакета и его транспорт; такие workers могут не иметь native parent ID.
   Совпадения каталога или имени `/root/...` недостаточно. Основной разговор, другие задачи
   и проектные файлы/отчёты/БД/резервы в эту уборку не входят.
3. Сверяет реальные состояния помощников. Активному ненужному агенту отправляет interrupt;
   после подтверждения останавливает его оставшиеся команды/терминалы штатными средствами.
   Завершённого без следующего поручения не держит в запасе.
4. Для полностью завершённой задачи вызывает штатный `thread/delete` по каждому проверенному
   дочернему UUID через доступный инструмент или поддерживаемый локальный App Server API.
   В CLI0.166.0 тот же штатный путь доступен командой `codex delete UUID --force`;
   применять только к подтверждённым дочерним UUID в разрешённой области.
   Этот метод закрывает поток и удаляет его журнал/метаданные; удаляет также потомков,
   поэтому их принадлежность и завершение тоже должны быть проверены. API сверяется
   с установленным CLI; адреса серверов и версии не угадываются.
   Если задаче ещё нужно продолжение, закрывает только больше не нужные потоки через
   close/shutdown или `set_thread_archived`, сохраняя журналы для приёмки/восстановления.
   В App Server завершает принадлежащие этому запуску дочерние потоки/процесс транспорта;
   `runBatch` уже закрывает свой клиент в finally. Закрытие транспорта не удаляет сохранённые журналы.
5. Подтверждает выгрузку: UUID отсутствует в `thread/loaded/list` либо `thread/read` показывает
   `notLoaded`/отсутствие потока. После удаления проверяет также отсутствие дочерней сессии
   среди сохранённых активных/архивных потоков и обновляет краткий итог уборки.
   `completed`, `archived: true` и ответ interrupt сами по себе не доказывают закрытие.

Если штатное закрытие/удаление недоступно или вернуло ошибку, сверяет фактическое состояние
и кратко сообщает, что именно осталось; не выдаёт попытку за успех. Допустимо штатно
архивировать уже принятую сессию с проверкой выгрузки, но это не удаление журнала.
Служебные метаданные можно читать для идентификации; SQLite и rollout-файлы вручную
не правятся и не удаляются. Основную задачу не архивирует, общий app-server не перезапускает
и чужие процессы не останавливает ради закрытия помощника.

Факт «completed» означает окончание работы агента, но не измерение освобождённой памяти.
В итоговом ответе различай число работающих, простаивающих загруженных и уже выгруженных
помощников; накопленная история запусков не становится лимитом одновременной работы.
Проверяй собственные оставшиеся процессы, не чисти чужие серверы/терминалы по одному похожему имени.
Новый помощник создаётся под нужную независимую работу, не для заполнения всех слотов.

- `stop` запрещает новую выдачу. В App Server runner прерывает собственные turns и проверяет
  собственные терминалы. Для штатных агентов команда возвращает ID — координатор обязан вызвать
  реальные средства остановки и проверить команды. Маркер/ответ interrupt не доказательство.
- При новой команде пользователя: status, проверка действующего AGENTS/плана, файлов,
  потоков/агентов и результатов. Живой lock не снимается и второй writer не создаётся.
- `recover` может снять только доказанно мёртвый PID-lock; running переводится в needs_review,
  **не pending**. Потерянный ответ на запись/миграцию/внешнюю команду сначала расследуется.
- После сверки: `retry <id> --reason '<установленный исход и почему повтор безопасен>'`;
  попытки ограничены, автоматических повторов модельных запросов нет. Изменённый контракт —
  новое поручение, не тихая замена старого. Запоздалый результат прежней попытки отклоняется.
- `resume` снимает стоп только по новой команде и после сверки running; самостоятельно не запускает
  модель. Затем claim/run именно разрешённого batch, не всей старой очереди.
- Принятый результат проверен на сохранённых отпечатках. Изменение после проверки или изменение
  правил/скилла требует адресной повторной сверки. Никаких повторов успешного неизменённого набора.

Тесты самого диспетчера: `npm run test:orchestration`. Они используют свои временные файлы
и фиктивный транспорт RPC; не поднимают приложение, БД, Docker или платные модельные turns.
