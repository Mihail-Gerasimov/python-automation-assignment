# Оркестрация проектной работы

Главное правило, актуальный AGENTS, согласованный план и разрешения выше этого скилла.
Инструкции не дают доступа к production, Git, данным или дополнительным стендам.

## Сначала определить свою роль

- **Координатор:** веди запрос пользователя целиком и принимай технический результат.
- **Исполнитель поручения** (`ORCHESTRATION_WORKER` или явная делегация): выполни только свой
  контракт, прочитай назначенные скиллы; не открывай свою очередь и не запускай помощников.
  Верни результат, затронутые файлы, проверки, ограничения и использованные справочники.
- Статус, объяснение и простой ответ не требуют очереди, приложения и команды помощников.
  «Проверь» означает проверку, а не разрешение исправлений. Бытовой чат вне этого процесса.

## Порядок координатора

1. Прочитай проектный контекст по AGENTS. Определи режим: подготовка плана, исполнение,
   проверка или короткий ответ. Для новой задачи назови цель и достаточную проверку.
2. Зафиксируй контракт в существующей фазе/задаче: границы, поведение, зависимости,
   реальные риски, нужные проверки. Продуктовые решения и расширение работы оставь заказчику.
3. Выбери применимые инструкции по таблице ниже. Прочитай их сам целиком до использования;
   помощник тоже читает свои инструкции. Справочники — только нужные, не весь комплект.
   Координатор и исполнитель обязаны полностью соблюдать
   [правило исполнения скиллов](../../../AGENTS.md#обязательное-исполнение-скиллов).
4. Раздели готовую независимую работу. Связанный сценарий с тестами имеет одного владельца;
   общие правила/DTO/схема — одного writer. Разные файлы не означают независимость.
   Порядок шагов сохраняется; параллельная группа шагов требует согласования в плане.
5. Назначь профиль по конкретным признакам, не числу строк/файлов. Единственный словарь
   моделей/effort — [config.json](./config.json); вычисление — `scripts/policy.mjs`.
   Риски сами по себе выбирают максимум `critical`; дополнительные effort Luna/Sol выбирай
   явно по [сложности поручения](./references/execution.md#выбор-и-достаточность).
   Astra — только high и отдельный адресный разбор по
   [условиям эскалации](./references/execution.md#когда-подключать-astra).
   Ultra — профиль основного координатора, не вложенного исполнителя; конфиг не переключает сессию.
   Проверь доступность в текущей среде; недоступный профиль не заменяй молча более слабым.
6. Для подготовки и реализации делегируй только необходимую независимую работу в пределах
   свободных слотов, максимум три помощника одновременно. Три — потолок, не квота.
   Не создавай внешний пул в обход ограничений сессии. Нет независимой работы — делай сам.
7. Прими результат по итоговым изменениям и фактическим проверкам. Сообщение «готово» и
   `turn/completed` не доказывают приёмку. Сам проверь выполнение применимых обязательных
   требований назначенных скиллов по всему результату. Для кода прочитай итоговые изменения
   и проверь ответственность модулей, переиспользование и читаемость по `code-simplifier`;
   зелёные тесты проверяют поведение и не заменяют эту проверку структуры.
   Невыполненные требования исправляются до приёмки; ограничения фиксируются явно.
   Документы синхронизируй один раз на законченный блок.
   Если блок включал БД-тесты, Docker-сборки или создание временных копий, заверши его по
   [локальной гигиене AGENTS](../../../AGENTS.md#локальная-гигиена-ресурсов); общую уборку ведёт координатор.
8. После приёмки блока [закрой ненужных помощников и проверь их команды](./references/execution.md#завершение-помощников).
   Когда задача завершена целиком и результаты сохранены, штатно удали её дочерние сессии
   вместе с журналами по тому же порядку. Это постоянное поручение, повторное разрешение не нужно.

## Маршрутизация скиллов

| Признак поручения                                   | Применение                                                |
| --------------------------------------------------- | --------------------------------------------------------- |
| Подготовка продуктового решения/фазы                | `product-planning`; один существующий план, не второе ТЗ  |
| Ценность, запись/покупка, первая польза, удержание  | `product-marketing` при формировании/пересмотре решения   |
| Новый UI, редизайн, визуальная правка               | `visual-design`; точечная правка не становится редизайном |
| Новая/исправляемая логика                           | `tdd`; исполнитель ведёт RED → GREEN → Refactor           |
| Планирование нового поведения                       | `tdd` только для выбора будущих проверок, без запуска RED |
| Написание/рефакторинг исходного кода                | `code-simplifier` с начала работы и итоговый проход по всему блоку |

Чистый рефакторинг сохраняет покрытие; косметика/текст не требуют новых поведенческих тестов.
Маркетинг не нужен технической задаче, simplifier — документации. Обязательные инструкции среды
дополняют таблицу. Недоступный нужный скилл требует явного решения о допустимом запасном пути.

## Поручение и исполнение

Контракт: `цель/шаг → режим и границы → зависимости → владелец → модель + effort →
скиллы → риски/проверки → критерий приёмки`. Признаки риска определяет координатор после
чтения задачи и кода, не поиск ключевых слов. Дополнительный effort требует конкретной причины
сложности в `reason`; Astra дополнительно требует `escalation`. Выбирай достаточный профиль
сразу, без обязательного расходования всей лестницы; результаты успешных проверок не повторяй.

- Для короткой самостоятельной работы достаточно контракта в запросе/фазе.
- Для параллельной/длительной работы используй сохраняемую очередь и порядок из
  [исполнения и восстановления](./references/execution.md). Очередь не заменяет статус фазы.
- Предпочитай штатные средства агентов сессии; модель и effort передавай явно.
  Не выдавай сохранённый профиль за фактические параметры, если инструмент их не позволяет.
- App Server — альтернативный исполнитель той же очереди, не второй одновременный пул.
  Его запуск требует подтверждённой доступной ёмкости; инструкции сами не являются демоном.
- Переиспользуй совместимый поток внутри ещё выполняемого связанного блока с конкретным
  следующим поручением. После приёмки блока он подлежит закрытию. Смена модели не стирает
  инструкции; несовместимый режим и независимое ревью требуют чистого потока с краткой передачей фактов.
  После удаления сессии новую задачу начинай чистым потоком с сохранённым результатом,
  не через `reuseFrom`/resume удалённого UUID.

## Восстановление и стоп

После перезапуска сверь правила, очередь, реальные запуски и актуальность результатов.
Старый `running`, неизвестный исход изменяющей команды или старый отчёт не разрешают повтор.
Нельзя иметь двух владельцев одной работы. Детали — в справочнике исполнения выше.

По «стоп» прекрати выдачу, останови помощников и проверь запущенные ими команды; сохрани факты.
История завершённых агентов не означает работающие процессы. Правило известного порога 95%
и ограничения production/Git остаются из AGENTS. Продолжение — по новой команде.
Называй непроверенное; экономию и отсутствие багов не обещай без измерений.
